# アイデア精査レポート — 2026-07-13

## 総評

今回の収集では、EigoCheckの直接拡張・ハンドメイド作家向けBtoC・運送業界BtoBの3方向でそれぞれ実現性の高いアイデアが揃った。全体的な傾向として「AIによる爆速MVP開発の恩恵を受けやすい・技術的にシンプルだが解決できる痛みが明確」なアイデアが上位に集中した。特にオーナーが業界インサイダーである運送業は、外部開発者には真似できない優位性を持ち、BtoBの高単価と合わせて収益化の確実性が最も高い。

## 🥇 第1位: EigoCheck ライティングコーチ拡張（ビジネス英語添削モード）

**総合スコア: 84/100**

| 評価軸 | スコア | コメント |
|--------|--------|----------|
| 実装難易度 | 19/20 | 既存のiOSキーボード拡張コード・OpenAI API連携・App Store申請ノウハウをそのまま流用。新規開発量は最小。1〜2ヶ月でMVP可能 |
| 市場規模 | 16/20 | 日本人英語学習者は推定2,000万人以上。特に「ビジネスメール・Slackを英語で書く社会人」層は500〜1,000万人規模。月500〜980円を払える購買力がある |
| 競合の少なさ | 14/20 | Grammarlyは英語UIで日本語解説なし。DeepLは「翻訳」で「添削」ではない。日本語解説付き英語ライティング添削キーボードはApp Storeで3件未満 |
| EigoCheckとの相乗効果 | 20/20 | EigoCheckそのものの機能拡張。既存ユーザーへの直接クロスセル、コード流用、スキル・知見・申請フロー全て活用。他のアイデアとは次元が違う |
| マネタイズ可能性 | 15/20 | 月額サブスク980円でEigoCheckユーザーの有料転換率15〜20%を目標にすれば、300人で月3万円。既存ユーザーへの通知・プッシュ施策から開始できる |

**なぜ今のオーナーに向いているか:**
既存のEigoCheckという「動く資産」があるため、ゼロからの新規開発ではない。「英語キーボードアプリを作った人が、さらに深く英語添削に特化した」という製品ストーリーが自然で、ユーザーへの説明コストが最も低い。Duolingo・Grammarlyへの不満（日本語解説なし・課金誘導強い）が明確なので、「日本人のための・日本語で理由を説明する英語添削」という差別化軸が今まさに有効。

**MVP設計案:**
- 最小機能: キーボード上のボタンで入力中の英文を送信→OpenAI APIで「修正案＋日本語でなぜそうなのかの説明」を表示→1タップで置換
- 技術スタック: Swift + iOS Keyboard Extension（既存流用）+ OpenAI GPT-4o mini API（コスト最小）+ RevenueCat（サブスク）
- 想定工数: 開発3〜4週間（APIプロンプト設計・UI調整・App Store審査で計2ヶ月）
- 最初の収益化方法: 月3回まで無料→980円/月でフリーミアム。EigoCheck既存ユーザーへのプッシュ通知告知

**リスク・注意点:**
- OpenAI APIのコストが使用量増加で増える（キャッシュ設計・トークン節約が重要）
- EigoCheckのダウンロード数が少ない場合、既存ユーザーベースが小さく初速が出ない可能性
- Grammarlyが日本語UI対応を強化してきた場合の競合激化リスク

## 🥈 第2位: 傭車管理シンプルiOSアプリ（中小運送会社向け）

**総合スコア: 74/100**

| 評価軸 | スコア | コメント |
|--------|--------|----------|
| 実装難易度 | 15/20 | Swift + RESTful API（自前バックエンド）。管理者（事務）とドライバーの2役割設計が必要で、EigoCheckより複雑。サーバーサイドも必要（Supabase等で代替可）。3ヶ月で傭車発注・精算管理の最小版は可能 |
| 市場規模 | 14/20 | 中小運送会社（10〜50台規模）は全国数万社。ただしBtoBのため顧客獲得が個別営業依存。初期20〜30社の獲得で月10〜20万円の現実的な目標 |
| 競合の少なさ | 19/20 | iOS専用の傭車管理アプリはほぼ存在しない。「トラDON」「そらうど」はPC/Web中心で、スマートフォンファーストの傭車管理は空白地帯 |
| EigoCheckとの相乗効果 | 4/20 | ユーザー層・技術スタック・ドメインがほぼ無関係。SwiftUIのスキルは流用できる |
| マネタイズ可能性 | 18/20 | BtoBのため月額5,000〜10,000円/社が現実的。20社獲得で月10〜20万円。法人経費なので価格感度が低く、チャーン率も低い。IT導入補助金（補助率1/2）の対象になれば導入ハードルがさらに下がる |

**なぜ今のオーナーに向いているか:**
デジタコ×運行管理システム会社に勤務している業界インサイダーであることが、このアイデアの最大の強み。「傭車管理の月末照合が2〜3日かかる」という痛みをリアルに知っている開発者が作るアプリは、競合他社が真似できない解像度を持つ。また現職の人脈で最初の5〜10社へのパイロット導入を打診できる可能性がある（営業コストゼロに近い）。

**MVP設計案:**
- 最小機能: ①傭車先への発注記録（日付・便名・金額）②月末に一覧PDF出力③照合チェックボックス。管理者iOSアプリのみ（ドライバーアプリは後回し）
- 技術スタック: SwiftUI + Supabase（バックエンド/DBをゼロから作らない）+ PDFKit（PDF出力）
- 想定工数: 開発6〜8週間 + ユーザーテスト（知人運送会社）2〜3週間 = 計3ヶ月でMVP
- 最初の収益化方法: 初期5社に月3,000円（ベータ価格）でパイロット提供→フィードバック反映→正式価格5,000〜10,000円へ

**リスク・注意点:**
- BtoBのため「導入先の担当者の承認取得」に時間がかかる可能性（稟議が必要な会社も）
- 月末の請求照合ロジックが各社ごとに異なり、カスタマイズ要望が出やすい
- 現職との利益相反が生じないか確認が必要（競合サービスとの関係）
- サーバーの維持コストが発生（Supabase無料枠で初期はゼロだが、規模拡大で有料化）

## 🥉 第3位: ハンドメイド作家向け在庫×原価管理iOSアプリ（minne/Creema対応）

**総合スコア: 73/100**

| 評価軸 | スコア | コメント |
|--------|--------|----------|
| 実装難易度 | 18/20 | SwiftUI + Core Data（ローカル）またはCloudKit（iCloud同期）のみで成立。外部API不要。最もシンプルな技術スタック。2〜3ヶ月でMVP可能 |
| 市場規模 | 15/20 | minne登録作家数100万人以上。複数プラットフォーム出品者を10万人と仮定すると、月額980円×1%転換で月100万円のポテンシャル。ただし認知獲得のマーケティングが課題 |
| 競合の少なさ | 16/20 | Shippo Tools（Web/無料）が存在するがiOSネイティブアプリではない。iOS App Storeでの直接競合は2〜3件。App Store検索流入が期待できる |
| EigoCheckとの相乗効果 | 10/20 | SwiftUIスキル・Core Dataの経験・App Store申請フローが流用できる。ユーザー層（ハンドメイド作家）はEigoCheckユーザーとほぼ重ならない |
| マネタイズ可能性 | 14/20 | 月額980〜1,980円で最初の100人達成が目標。App Store検索流入が主な獲得チャネル。6ヶ月以内に月3万円を目指すなら100人転換が必要で、マーケティング施策（note記事・minne公式連携等）が必須 |

**なぜ今のオーナーに向いているか:**
技術的な実装難易度が最も低く、EigoCheckで習得したSwiftUI・App Storeのノウハウをそのまま転用できる。市場（ハンドメイド作家コミュニティ）はSNSで活発でバイラルしやすい。ドメイン知識は不要（「在庫と原価を管理したい」というニーズはシンプル）なため、ユーザーインタビューをしてから実装することも容易。

**MVP設計案:**
- 最小機能: ①材料の登録・在庫数管理 ②作品の材料レシピ登録→原価自動計算 ③売上記録（プラットフォーム別）④利益率の表示
- 技術スタック: SwiftUI + Core Data + CloudKit（iCloud同期） + RevenueCat（サブスク）
- 想定工数: 開発4〜6週間 + App Store審査2週間 = 計2ヶ月でMVP
- 最初の収益化方法: 3作品まで無料（完全機能）→4作品以降は月額980円。noteとX（Twitter）でハンドメイド作家コミュニティに告知

**リスク・注意点:**
- Shippo Toolsが有料化・iOS対応を強化してきた場合の競合激化
- BtoCのため広告・SNS集客コストがかかる（EigoCheckと同様のユーザー獲得課題）
- minne/Creema APIが公開されていないため「在庫自動同期」はできず、手動入力が前提になる（UX上の弱点）
- ハンドメイド市場は女性ユーザーが主体。UIデザインの完成度が評価に直結する
